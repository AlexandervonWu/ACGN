# A2-23 ordered dependent ARROW products

The original A2-23 ledger statement requires an ordered Cartesian product with source order and repeated occurrences. The Phase A2 contract specifies `cols(R) ++ cols(S)` and a multiplicity-preserving variadic `Seq` over source operands. Neighboring A2-21 separately requires duplicate product alternatives to be removed during family normalization. [Original ledger](../../section3-repair-audit/claim-ledger.md) · [Phase A2 contract](../../section3-repair-audit/phase-a2-dependent-chains.md) On an admitted `DependentTypeDag`, a family already contains whole products sorted by structural `GraphType` order. `combine(ARROW, left, right)` enumerates the left family on the outside and the right family on the inside. Case `i * right.size() + j` has the two source ordinals, the ARROW decision, no JOIN boundary and every original left column occurrence followed by every original right occurrence. A repeated column keeps both positions. The binary chain application likewise concatenates the source leaf sequences and retains a repeated source slot.

Before combination, the DAG constructor groups equal exact product keys, checks compatible ancestry, prefers an authenticated duplicate representative, removes strictly subsumed products and sorts the remaining alternatives. A raw listing such as `[Z, A, A]` becomes the two ordered alternatives `[A, Z]`. The `Int` kind orders before nominal signature constructors, including `AlloySig:A`. These rules concern alternative rows. They never sort or deduplicate columns inside a row. Neither a raw union's presentation order nor its number of equal alternatives is an invariant of the represented relation.

## General result

The Lean model permits arbitrary finite families and arbitrary column evidence with a separate projection to exact type keys. An admitted operand has a fixed positive width, strictly lexicographically ordered keys and an antichain under the supported coordinatewise weak-subtype relation. Splitting that relation at the common left width shows that concatenation cannot introduce strict subsumption. Equal left keys have an equal fixed-width prefix; distinct right keys retain their order behind it. Strictly ordered left keys decide the full comparison independently of the right suffix. Consequently the products already have distinct, sorted keys, the strict-absorption pass retains every row, and normalization preserves even the original evidence objects in the list model. The proof also covers the count, individual row ordinal, duplicate column count, width, empty families and arbitrary reassociation of nested products.

The final theorem derives those operand properties from the modeled constructor. It proves that grouping by exact product key preserves uniform width and yields unique keys under the actual authenticated-duplicate preference. Testing every candidate against every other candidate guarantees the surviving antichain even without assuming transitivity of the evidence relation. Sorting gives strict product order on the unique keys. The comparator uses the INT and nullary nominal tags, UTF-16 units of signature symbols, and lexicographic product arguments. Applying the same constructor again to an ordered ARROW product returns exactly its original evidence rows. For source trees, erasing the left/right path annotations of all located leaf occurrences gives the ordered leaf sequence at every association. The Java compiler witness resolves seventeen production methods or constructors. Its nineteen-instruction output covers both counted loops and indexed reads, the case writes, admission, grouping, absorption, sorting, type comparison, freezing, result construction, and left-to-right leaf collection. The registered Lean decoder reads that file. Its accumulator and constructor proofs give the ordered product for every pair of successfully admitted fixed-width input families. Swapping the operands and replacing sorting with reversal both produce type-correct Java and both compiled instruction streams are rejected by Lean. A separate full method-body and resolved-call digest also changes in both cases.

## Executable boundary

`A223ArrowCases.verify` checks any supplied admitted pair and actual `ChainCombination` at the public Java boundary, independently of the production solver. It computes the source address of every output position and checks the identity of the column in both the decision matrix and the normalized DAG. It also checks the typed width and cardinality for empty operands. The focused witness exercises 128 pairs, including 23 typed-empty pairs and 384 nonempty product rows. Additional cases cover raw Alloy correlation and subtype absorption, authenticated duplicate selection in both orders, conflicting stacks, foreign parser authority, foreign equal-key occurrences, mixed widths, invalid empty arity, checked integer overflow and repeated leaves across both associations.

The source-to-model boundary trusts the registered Java tree decoder, compiler and JVM, JDK implementations of ordered maps, comparisons and sorting, and the supplied parser authority. The proof derives the order and antichain properties for arbitrary raw rows traversing the registered successful constructor stages. Its subtype test is parameterized by the authenticated per-coordinate decision; no transitivity or completeness assumption about that decision is used to prove the ARROW result. Complete verification of every producer of such evidence, arbitrary raw Alloy parsing and a semantics of the entire JVM are outside this registration. Actual Java execution also requires sufficient allocation and representable integer sizes for arities and materialized matrices. The public tests found no production defect.
